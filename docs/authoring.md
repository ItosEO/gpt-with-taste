# Change the recipe once

Edit `recipe/`, then build. Every harness receives the same behavior through its own prompt and event interfaces.

```sh
node scripts/build.mjs
node scripts/build.mjs --check
```

The build runs locally. Generated files are committed, so people installing from a clone can use the existing Codex installer without building first.

## Where to edit

`recipe/manifest.json` names six complete English instruction sources:

- `main.md`: judgment, execution, collaboration, and final delivery.
- `sub.md`: complete scoped work within the parent's role contract.
- `independent.md`: neutral work principles for a host without a parent controller.
- `user-steer.md`: reconnect incoming user input to the ongoing assignment.
- `sub-steer.md`: continue the delegated scope and resolve ordinary local work.
- `agent-steer.md`: consume collaborator evidence, decide, and route useful increments.

Edit a source where its responsibility lives. Keep revisions integrated into the existing paragraph, then read the complete affected instruction. Research stays conditional; ordinary development does not acquire a mandatory scientific workflow. Reply language follows the user, while project artifacts follow their own conventions.

`adapters/` owns harness-specific loading, identity, message events, and packaging. `dist/` contains generated artifacts. The old `prompts/` paths are generated Codex compatibility exports, so the installer and optional plugin retain their existing entry points.

The package version lives in the recipe manifest. Its Kiki compatibility metadata retains the previous Sol/Astra package IDs, version, and exact four-alias map. Revisions can change without a version bump during refinement.

## Build one target

```sh
node scripts/build.mjs --target kiki
node scripts/build.mjs --target claude --check
```

Repeat `--target` to select several. A targeted build loads only those adapters. `--check` compares expected bytes with the explicit output list and reports stale or missing artifacts without writing.

Model-facing Markdown and text resources preserve the behavior source verbatim. Author paths, source versions, generator names, and rebuild instructions belong in sidecar metadata, separate from prompt bodies and callback context. Each `dist/<harness>/build-manifest.json` records the author paths, adapter, source version, and generated files; adapter-specific `PROVENANCE.md` files retain transport attribution. For the managed Kiki operations checkout, its `build-sol-astra.mjs` bridge checks this same compiler output before mirroring the compatibility files.

## Add a harness

Create `adapters/<id>/build.mjs` with this export:

```js
export async function render({ root, meta, texts }) {
  return new Map([
    ['main.md', texts.main],
    // Native manifests, prompt files, and event adapters for this harness.
  ]);
}
```

The Map's keys are paths relative to `dist/<id>/`. Values are strings or Buffers. `texts` contains `main`, `sub`, `independent`, `userSteer`, `subSteer`, and `agentSteer`. The renderer produces files; it does not install them or contact a service. Register the ready target in `src/build.mjs`.

Use the harness's actual API and preserve its built-in tool, environment, role, and project context. Identify Main and Sub from a real runtime field or an explicit role selection. For Steer, confirm which agent consumes an event and when its context reaches the next model request. Keep original tool results intact. Handle runtime extension code inside that adapter rather than adding harness-specific conditions to the shared behavior text.

Add a consumer test that loads the actual generated module or manifest, exercises the relevant native callback with representative inputs, and checks role, source, placement, and repetition. Include the failures that could change installation or use. Reuse valid checks for unchanged code; model calls are not required for compilation, discovery, or event-routing fixtures.

Write the harness's activation, update, and removal steps in `docs/harnesses/<id>.md`. Then build it, check the generated bytes, and include its focused tests in the repository test command.

## Publish a change

Review the author diff alongside the generated diff. Check the affected adapter, existing consumers, instructions, and recovery path. Commit author sources and their generated files together. Install from the chosen local revision using the harness guide; manual update checks report available source changes without downloading or applying them.
